# Память на часовых сессиях: CaImAn 1.13.2 (итог разведки, задача 0.3)

2026-10-31. Окружение `bearmind` (CaImAn 1.13.2, NumPy 2.5.4, OpenBLAS), Windows 11, 32 логических ядра. Продолжает `2026-10-31-caiman-memory-prelim.md` (1.11.3). Решения автора от 2026-10-31: детерминизм не проверялся и не навязывается; out-of-core `compute_W` не реализуется (в TODO), здесь только ответ, нужен ли он.

Метки: **[изм]** замерено на 1.13.2; **[код]** прочитано в исходниках 1.13.2 (сравнение с 1.11.3 через diff); **[вывод]** экстраполяция или предположение.
Методика та же: синтетика, отдельный процесс на шаг, пик private bytes Windows минус базовый уровень процесса после импортов. Скрипты и сырые результаты: scratch `memrecon113/` (`results_patch113.jsonl`, `results_global113.jsonl`). Реальные данные не использовались.

## Главное

1. **Память CaImAn почти не изменилась между 1.11.3 и 1.13.2.** Все семь горячих точек остаются на тех же строках кода с теми же множителями. Правки, предложенные в предварительном отчёте, остаются нужны. [изм + код]
2. **`patch_gb_per_mframe`** (воркер патча CNMF-E, ГБ на миллион кадров): **tsub=1: 242** (9.22 единицы), **tsub=2: 163** (6.21 единицы). Значения из плана (245 и 163) остаются верными и чуть консервативны; менять тесты Task 10 не нужно. [изм]
3. **`compute_W` в 1.13.2 по-прежнему материализует весь фильм**: 5.0 × T·d при float64 (A, C), 3.0 × T·d при float32. Код функции не изменён, `data_fits_in_memory=True` по умолчанию, `CNMF.fit` вызывает её без этого аргумента. Для часовой сессии это ~111 ГБ (450×450) и ~201 ГБ (608×608) в float64. [изм + код]
4. **Новое в 1.13.2, влияет на обёртку:**
   - `save_memmap` теперь добавляет к данным ровно `np.float32(add_to_movie)` с умолчанием `add_to_movie=0.0001` (раньше: `+0.0001 + add_to_movie`, двумя сложениями). Писатель memmap полосами обязан использовать одно сложение `blk + np.float32(1e-4)`; тогда файл совпадает побайтно (проверено). [код + изм]
   - `save_memmap` с `base_name` в виде полного пути всё равно кладёт файл в `get_tempdir()` (по умолчанию `C:\Users\User\caiman_data\temp`), а не рядом с `base_name`; возвращает полный путь. Каталог задаётся переменной окружения `CAIMAN_TEMP`. [изм]
   - `load_memmap` принимает ещё и `.npy`. Нам не нужно. [код]
5. **Базовый уровень процесса: 4.65 ГБ commit у каждого процесса после `import caiman`** (в 1.11.3 было 0.35 ГБ). Это не данные: OpenBLAS резервирует ~125 МБ адресного пространства на каждый из 32 потоков, рабочий набор процесса (working set) всего 0.55 ГБ. С `OPENBLAS_NUM_THREADS=1` commit = 0.67 ГБ. Прирост памяти патча при этом тот же (9.25 против 9.22 единицы), время не хуже (34.6 с против 38.5 с, T=8000, tsub=1). Рекомендация: ставить `OPENBLAS_NUM_THREADS=1` в окружении воркеров пула до их запуска. Тогда 31 простаивающий воркер не занимает ~144 ГБ лимита commit. [изм]

## Проверки идентичности на 1.13.2 [изм]

- Кусочное применение сдвигов `apply_shift_iteration(img_float32, shift, border_nan='copy')` кадр за кадром с потоковой записью `TiffWriter`: **файл побайтно совпадает** с `np.array(mc.apply_shifts_movie(...), uint8)` + `imwrite` (T = 1500 и 3000). Условия: `shifts_opencv=True` (умолчание параметров; при `False` CaImAn применяет другую функцию `apply_shifts_dft`), `pw_rigid=False`, `border_nan='copy'`, вход uint8, переведённый в float32.
- Запись memmap полосами по столбцам с `blk + np.float32(1e-4)`: файл **побайтно совпадает** с `cm.save_memmap(order='C')` (T = 1500 и 3000).
- Пик 3.03 × T·d в скрипте проверки применения сдвигов создают два `tifffile.imread` для сравнения, а не сам поток.

## Не мерилось

- Детерминизм CNMF-E и зависимость от размера пула (решение автора).
- Потоковый PNR на 1.13.2: `correlation_pnr` не менялась, значит, проверка от 1.11.3 (побитово на 600 кадрах) переносится по коду [вывод]; ветка более 3072 кадров по-прежнему предположение.
- Реальные патчи с большим числом seed (до +1.7 ГБ на воркер в 1.11.3) [вывод].
- Полный `CNMF.fit` с проверкой фактического dtype `A`, `C` при вызове `compute_W` (мерился изолированный вызов с float64 и float32); реальный множитель `compute_W` лежит между 3.0 и 5.0 × T·d.
- Числа при T = 108 000 экстраполированы с T ≤ 8000 (патч) и T ≤ 6000 (остальное): линейность по T подтверждена на трёх точках для патча, на двух для остального.

## Изменения для Tasks 8 и 10 (план не правился)

**Task 8 (MC):**
1. Шаг 3: добавить требование `mc.shifts_opencv is True` (иначе `apply_shifts_movie` в CaImAn использует `apply_shifts_dft`, и побитовое равенство из теста не выполняется). Обёртка проверяет это и падает с понятной ошибкой. Кадры подавать в `apply_shift_iteration` как float32 (из uint8), `border_nan='copy'`, `pw_rigid=False`.
2. Шаг 2: `splits_rig = ceil(T/500)` и `save_movie=False` подтверждены; уточнить, что пул MC берёт 14 воркеров, память воркера ~15.7 × (500·d), то есть ~22 ГБ (450²) / ~41 ГБ (608²) на этап.
3. Временные файлы: CaImAn 1.13.2 кладёт свои временные memmap в `get_tempdir()` (`C:\Users\User\caiman_data\temp`), а не туда, куда указывает `base_name`. Перед запуском этапа задавать `os.environ["CAIMAN_TEMP"] = machine.temp_dir/<sid>`, иначе очистка в `finally` их не найдёт.
4. В среде воркеров пула задать `OPENBLAS_NUM_THREADS=1` (иначе у каждого воркера 4.65 ГБ commit).

**Task 10 (CNMF-E):**
1. `patch_gb_per_mframe`: замер 242 (tsub=1) и 163 (tsub=2). Значения плана 245 и 163 оставить (запас ~1%); тест `test_patch_workers_budget` остаётся верным (5, 8, 31).

Эталон в `test_memmap_strips_identical_to_save_memmap` брать из пути, который вернул `cm.save_memmap` (файл лежит в `CAIMAN_TEMP`, не рядом с `base_name`), вызывать без `add_to_movie`.

Фраза «кадр 608×608 на часовой сессии пока не обрабатывается без кропа» остаётся в силе: при бюджете 153 ГБ (0.8 × 192) 450×450 влезает (111 ГБ float64), 608×608 не влезает в float64 (201 ГБ), а в float32 (120 ГБ) влезает формально, но вместе с остальным не гарантировано.
