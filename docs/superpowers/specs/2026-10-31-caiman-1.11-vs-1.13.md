# CaImAn 1.11.3 vs 1.13.2: measured differences (Task 0.4)

Date: 2026-10-31. Machine: Windows 11, 32 logical cores, 192 GB RAM.

## Result in one paragraph

Motion correction (MC) gives the same shifts in both versions (max |diff| 0.1 px over 11849 frames).
The legacy CNMF step (`DoCNMF`, notebook parameters) could NOT be compared:
under CaImAn 1.13.2 / NumPy 2.5 the Python process dies with a Windows access violation
(`openblas.dll`, exit without traceback) inside `compute_W` (ring-model background, used because `nb=0`).
It crashed in 5 of 5 attempts; 1.11.3 finished every time. Component matching, trace correlation and SNR comparison
between versions are therefore NOT measured. This blocks the migration of the CNMF stage to the `bearmind` env
until the crash is fixed or worked around.

## Method

- Sessions: only NOF_H01_1D was run (CNMF takes 27 min on 1.11.3 for 11849 frames; the time budget did not allow a second session).
  NOF_H02_1D was built (11848 frames) but not run.
- Input: 12 AVI chunks concatenated without frame dropping (11849 frames = 11849 timestamps), channel 0, cropped `[8:, 8:]` to 600x600,
  uint8 TIF written once and copied for both environments. FPS from timestamps (median interval) = 19.758, not halved.
- Environments: `caiman` (CaImAn 1.11.3, NumPy 1.26.4, MKL) and `bearmind` (CaImAn 1.13.2, NumPy 2.5.4, OpenBLAS).
- Code: the repo's own `DoMotionCorrection` and `DoCNMF` from `bm_batch_routines.py`, unmodified. A driver script
  (scratch, not in the repo) forced the cluster size: `DoMotionCorrection` hard-codes 14 processes; `DoCNMF` uses `n_processes=None`,
  which the driver patched to 16 in `cm.cluster.setup_cluster` for both versions. `MotionCorrect` was subclassed in the driver only to read `shifts_rig`.
- Parameters: notebook `mc_dict` (rigid, max_shifts 35, gSig_filt 8, splits_rig 20) and `cnmf_dict`
  (corr_pnr, gSig 4, gSiz 17, min_corr 0.92, min_pnr 7, p 1, tsub 1, ssub 1, rf 40, stride 25, nb 0, ssub_B 2, ring_size_factor 1.5,
  min_SNR 2.5, rval_thr 0.95, use_cnn False, fr = 19.758).
- Planned comparison (script ready, not run for lack of 1.13.2 output): Hungarian matching of A columns by cosine similarity, matched if > 0.9,
  median trace correlation of matched pairs, SNR quantiles.

## Crash diagnosis (measured)

- Attempts that crashed on 1.13.2: full session twice (after 14 and 16 min), 3000 frames twice (one with `OPENBLAS_CORETYPE=Haswell`),
  600 frames in a single process. `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `OMP_NUM_THREADS=1` did not help.
- `faulthandler` stack of the single-process run: `cnmf.py:497 fit` -> `initialization.py:1968 compute_W`,
  the line `ds(A).dot(decimate_last_axis(C, tsub))` (dense `A.toarray()` times `C`, ssub_B = 2). The failure is in the main process, so it does not depend on the multiprocessing pool.
- Windows event log: faulting module `openblas.dll`, exception 0xc0000005.
- Inferred, not tested: a bug or incompatibility in the OpenBLAS matrix product bundled with NumPy 2.5.4 on this CPU,
  triggered by this dense product. Untested remedies: other NumPy 2.x or OpenBLAS build, `nb=1` with the standard background model
  (changes the science), `ssub_B=1`.

## Inferred, not measured

- That 1.13.2 gives the same components as 1.11.3 on this data: no evidence either way.
- Whether `NOF_H02_1D` behaves like `NOF_H01_1D`.
- Interleaved runs of both versions (shared CPU) affect wall times only, not results; the 1645 s figure is not a clean benchmark.

## Side effects found while running

- `DoCNMF` writes its memmap to `~/caiman_data/temp` under the TIF base name, so two concurrent runs on files with the same base name collide
  (`FileExistsError` on the second). The runs here were given distinct base names.
- Spawned workers re-import the main script, so a driver needs an `if __name__ == "__main__"` guard on Windows.
