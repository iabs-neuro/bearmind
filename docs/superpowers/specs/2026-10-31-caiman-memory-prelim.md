# Память на часовых сессиях: предварительная разведка (CaImAn 1.11.3)

2026-10-31. Субагент-разведчик, окружение `caiman` (CaImAn 1.11.3), код BEARMiND на `0628328`. Синтетические видео, отдельный процесс на каждый шаг, пик private bytes Windows минус базовый уровень. Скрипты и сырые результаты: scratch `memrecon/` (gen.py, patch_test.py, global_test.py, cnmf_np_test.py, mkl_test.py, peakstack.py, results_*.jsonl). Реальные сессии не замерялись. **Номера строк CaImAn — для 1.11.3; задача 0.3 плана перепроверяет всё на 1.13.2.**

## Главное

1. Семь отдельных шагов требуют > 100 ГБ при T = 108 000 кадров; четыре из них > 192 ГБ даже при кадре 450×450. Каждый шаг линеен по T (замерено на 2–3 значениях T).
2. Самое крупное — воркеры патчей CNMF-E: ~17.6 ГБ на воркер при `tsub=2`, ~26.4 ГБ при `tsub=1`. По умолчанию воркеров 31 (`n_processes=None` = 32 логических ядра − 1) → 546–818 ГБ. Память воркера не зависит от размера кадра (патч всегда 81×81 при `rf=40`). Дешёвый рычаг — пул из 4–6 воркеров на этап патчей.
3. **Размер пула меняет результат CNMF-E (замерено).** Синтетика 160×160×1500, 9 патчей, `cnmf_dict` ноутбука, `tsub=2`: пул 2 против пула 5 → K = 197 против 195, отличаются A, C, S, YrA, W, b0, idx, SNR, r_values. Тот же пул повторно — побитово одинаково. Причина (замерено на одном патче): результат зависит от числа потоков MKL (16, 4, 1 поток дают разные биты; 16 дважды — одинаковые). Вывод (предположение): динамический выбор потоков MKL зависит от загрузки CPU другими воркерами. Следствие: побитово одинаковый CNMF-E при любом изменении параллелизма невозможен; нынешний конвейер, вероятно, не воспроизводится между машинами с разным числом ядер.
4. Всё вне этапа патчей можно сделать плоским по памяти без изменения результата. Побитово проверены три замены: запись memmap полосами, применение сдвигов кусками, потоковый PNR. Сдвиги MC не меняются от `splits_rig` и `save_movie`.
5. Глобальный `compute_W` из обёртки не чинится: 5 байт на пиксель-кадр (109 ГБ при 450², 200 ГБ при 608²). Нужен monkeypatch или правка CaImAn.

## Минимальный набор, чтобы уложиться в ~120 ГБ при T = 108 000

1. Кроп: поток кадров во временный tif.
2. MC: `splits_rig=ceil(T/500)`, `save_movie=False` → 24 / 43 ГБ.
3. MC: применение сдвигов кусками с потоковой записью → ~1–3 ГБ.
4. Запись memmap полосами вместо `cm.save_memmap` → единицы ГБ.
5. Пул патчей 6 (`tsub=2`) или 4 (`tsub=1`) → ~107 ГБ. **Меняет результат.**
6. Out-of-core `compute_W` → < 10 ГБ (предп.).
7. Потоковый PNR для `imax` → 5 / 9 ГБ.

После этого пик — этап патчей, ~107 ГБ, задаётся размером пула. Без правки `compute_W` 450² на грани, 608² невозможно.

Время с малым пулом (предп.): патч 23 с (`tsub=2`) / 34 с (`tsub=1`) при T = 8000 → 5–8 мин на патч при 108 000; ~1–1.5 ч на 64 патча на 6 воркерах (450²), ~2–3 ч на 121 патч (608²).
