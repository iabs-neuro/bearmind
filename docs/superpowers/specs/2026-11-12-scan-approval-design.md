# Скан: подтверждение исправлений, серии без таймстемпов, стандартные длительности (дизайн)

Записка к пунктам 9, 10, 11, 13 (и связанным 16, 19, 20, 22) списка `2026-11-11-lt1-feedback.md`. Факты о текущем коде и о LT1 взяты из отчёта `docs/data-flow/index.html` (разделы 4–6) и из реестра LT1 (только чтение, 12.11.2026).

## Коротко

Цель: каждое изменение кадров видно автору и идёт под его контролем; серии без таймстемпов проходят батч; сессии с длительностью не по протоколу заметны сразу.

Нужны три решения автора. Без ответа делаю по рекомендации.

| № | Вопрос | Рекомендация |
|---|---|---|
| 1 | Флажок «исправлять аномалии автоматически»: включён или выключен по умолчанию для новой серии? | Включён (как сейчас). Автор выключает его в серии, где хочет смотреть каждое исправление. На LT1 флажок ничего не меняет: все сессии уже прошли кроп. |
| 2 | Серии без таймстемпов: откуда брать FPS? | Только от человека: FPS сессии, длительность сессии или одно значение на серию. Заголовок AVI — только подсказка с предупреждением, автоматически не используется. Причина: у всех 84 сессий LT1 в заголовке 20,0 к/с, у 60 из них это неверно на 33 %. |
| 3 | Стандартные длительности: как задавать? | Автоматически по серии плюс необязательный список в конфиге серии. Допуск max(2 с, 0,1 %), зона предупреждения ±25 %. На LT1 правило отмечает ровно 4 сессии (раздел 3). |

Порядок работ (раздел 5): сначала мелкие правки отображения (пп. 10, 12, 19), потом длительности (п. 13), потом подтверждение (п. 9) и серии без таймстемпов (п. 11). Всё делается в копии `bearmind-fixes` и переносится после остановки батча LT1.

## 1. Подтверждение исправлений (п. 9, с ним п. 22)

### Сейчас

Скан сам меняет кадры в четырёх случаях. Батч идёт дальше без вопроса.

| Аномалия | Что делает программа | Кадры |
|---|---|---|
| `broken_last_frame` | отбрасывает нечитаемый последний кадр | −1 |
| `chunk_tail_frames` | отбрасывает последний кадр каждого чанка, кроме последнего | −(чанков − 1) |
| `frames_ts_mismatch` ≤ 2 % | режет часть до общей длины **с конца** | −разница |
| `split_recording` (warning) | склеивает части по времени старта; Confirm stitch — только отметка, батч её не ждёт | паузы между частями исчезают для MC и CNMF-E |

`frames_ts_mismatch` > 2 % — ошибка: сессия исключена, пока человек не нажмёт Accept. Accept не привязан к конкретному расхождению (п. 22). После замены файлов он понижает до FIXED любую новую ошибку того же кода.

### Предложение

1. Настройка серии `scan.auto_fix` (true / false, по умолчанию true). На вкладке Scan — флажок **Fix anomalies automatically**; он пишет значение в `_bearmind/config/series.yaml`.
2. Флажок включён: всё как сейчас. Ошибки ждут человека, предупреждения исправляются сами.
3. Флажок выключен: каждая аномалия с исправлением ждёт подтверждения. Сессия получает состояние `waits: scan approval` во вкладках Scan и Monitor и в `bearmind status`. Батч не начинает её кроп. Остальные сессии идут дальше.
4. Панель Details показывает для каждой такой аномалии: что найдено (числа), предложенное исправление, другие варианты и кнопку Approve.
5. Подтверждение — решение в реестре `scan_fix` со значением «отпечаток аномалии + выбранный вариант». Отпечаток — код, часть и числа (например `frames_ts_mismatch|part 0|diff 107`). После Rescan та же аномалия остаётся подтверждённой. Изменилась — программа спрашивает снова. Так устроен уже Confirm stitch.
6. Accept для ошибки > 2 % становится тем же механизмом. Это закрывает п. 22: подтверждение относится к конкретной разнице.
7. Выделено несколько строк — кнопка **Approve proposed fixes (N sessions)**. Обычный случай решается одним нажатием.
8. Сессии, у которых уже есть готовые этапы, флажок не трогает. Их исправление уже применено; Details пишет «applied automatically».
9. Хэши этапов не меняются. Выбранный вариант меняет части и число кадров, а они уже входят в хэш кропа.

Варианты по аномалиям:

| Аномалия | Предложено | Другие варианты | Ждёт при выключенном флажке |
|---|---|---|---|
| `broken_last_frame` | отбросить последний кадр | исключить сессию | да |
| `chunk_tail_frames` | отбросить хвостовые кадры чанков | исключить | да |
| `frames_ts_mismatch` ≤ 2 % | обрезать с конца | исключить; (обрезать с начала — см. ниже) | да |
| `frames_ts_mismatch` > 2 % | исключить (как сейчас) | обрезать с конца | да, всегда |
| `split_recording` (warning) | склеить по времени старта | взять одну часть; исключить | да |
| новая: битая строка таймстемпов (п. 16) | отбросить немонотонные строки в конце | исключить | да |
| `dropped_frames`, `fps_outlier`, `no_metadata` | исправлять нечего | исключить | нет, только показ |
| `unreadable_video`, `no_timestamps`, `fps_unavailable`, `not_found_in_scan` | подтверждением не исправить | файлы → Rescan; для `no_timestamps` — раздел 2 | — |

**Обрезка с начала.** Программа не знает, на каком конце лишние кадры. Надёжного признака в данных нет. Вариант требует нового поля части (сколько кадров пропустить в начале), правки чтения видео и тестов. Рекомендация: не делать, пока не появится реальный случай.

## 2. Серии без таймстемпов (п. 11, с ним п. 20)

### Сейчас

Нет файла таймстемпов → `no_timestamps` (error) → `fps_unavailable` → сессия исключена всегда, Include не помогает. Падения нет, но и обработки нет. Заголовок AVI программа не читает как FPS. Кроме FPS, таймстемпы нужны экспорту (файл таймстемпов, `bearmind/stages/export.py:147`) и странице инспекции (ось времени, `bearmind/inspect_server.py:206`). Хэш экспорта включает файл таймстемпов (`bearmind/runner.py:292`).

### Предложение

1. Источник FPS по приоритету:
   1. таймстемпы (как сейчас);
   2. значение человека для сессии: FPS или длительность; второе считается: FPS = кадров / длительность;
   3. значение человека для серии: `scan.fallback_fps` в `series.yaml`, для установок без таймстемпов.
2. Заголовок AVI — только подсказка в диалоге: «AVI header: 20.0 fps — check». Автоматически не используется.
3. Диалог **Set frame rate…** на вкладке Scan (несколько строк сразу) и команда CLI `bearmind decide set-fps`:

```
Set frame rate: 3 sessions selected (17 855 frames each)
  (*) frame rate   [ 29.78 ] fps    -> duration 9 min 59.6 s
  ( ) duration     [ 10:00  ] min:s -> 29.758 fps
  AVI header: 20.0 fps (check: wrong on some Miniscope setups)
  ! 29.78 differs from the other sessions of J10 by 0.0 %
                                        [ Apply ]  [ Cancel ]
```

4. В реестре: `rec.fps`, `fps_info.source` = `manual_fps` / `manual_duration` / `series_fps`, решение с автором и временем. Колонка FPS показывает метку: `29.78 (manual)`.
5. Когда FPS задан, `no_timestamps` становится warning: «frame times are synthetic (k / fps); dropped frames cannot be detected». Сессия больше не исключена.
6. Экспорт пишет синтетический файл таймстемпов t<sub>k</sub> = k · 1000 / FPS и пишет в provenance `timestamps_source: synthetic`. Страница инспекции берёт те же времена. MC, CNMF-E и автоинспекция берут FPS как сейчас.
7. Часть с таймстемпами и часть без: склейка по времени невозможна. Вся сессия идёт на FPS человека; пауза между частями неизвестна → warning.
8. Точность: «10 мин» по протоколу против реальных 599,5 с LT1 — ошибка FPS 0,08 %. CNMF-E берёт `fr` только для окон оценки компонент, автоинспекция округляет FPS до целого. Этой точности хватает.
9. Тест: серия-копия тестовых данных без файлов таймстемпов (исходные данные не трогать) проходит скан, батч до экспорта и страницу инспекции.

## 3. Стандартные длительности (п. 13)

### Факты LT1

Длительность = кадров / FPS, как в колонке Min вкладки Scan.

| Группа | Сессий | Диапазон | Медиана |
|---|---|---|---|
| ≈ 10 мин | 42 | 599,2–599,7 с | 599,5 с |
| ≈ 40 мин | 38 | 2398,8–2399,9 с | 2399,7 с |
| вне групп | 4 | LT1_J55_4D 630,4 с (10,5 мин); LT1_J30_2D 656,1 с (10,9); LT1_J14_3D 677,7 с (11,3); LT1_J05_1D 2394,6 с (39,9: обрезанные таймстемпы, 107 кадров отрезано, п. 16) | — |

Разброс внутри групп 0,5 с и 1,1 с. «39 минут» во вкладке Scan — это LT1_J05_1D (39,9).

### Правило

1. Стандарты: список `scan.standard_durations_min` в `series.yaml` (например `[10, 40]`). Если списка нет — группы из ≥ 3 сессий и ≥ 10 % серии, у которых длительность в пределах допуска от медианы группы. Стандарт группы — её медиана.
2. Допуск: max(2 с, 0,1 % стандарта). Это 2 с при 10 мин, 2,4 с при 40 мин, 3,6 с при 60 мин. В LT1 он в 2 раза шире разброса групп.
3. Сессия в допуске — норма. В пределах ±25 % от стандарта, но вне допуска — WARN `nonstandard_duration`: «11.3 min; standard 10.0 min (+1.3 min)». Дальше ±25 % от всех стандартов — INFO: «25.0 min is not near the standards 10.0, 40.0».
4. Аномалия не исключает сессию и не ждёт подтверждения: исправлять нечего. Ячейка Min подсвечена. В шапке вкладки: «Standard durations: 10.0 min (42), 40.0 min (38)».
5. Сессия с длительностью от человека (раздел 2) не проверяется: длительность там задана, а не измерена.
6. На LT1 правило даёт WARN ровно у 4 сессий: J55_4D, J30_2D, J14_3D, J05_1D. У J05_1D отклонение 5,1 с, допуск 2,4 с.

## 4. Потерянное время в разрывах (п. 10, с ним п. 19)

П. 10 принят: показать суммарное потерянное время (мс) и кадры; рядом с FPS — колонка интервала между кадрами в мс.

Проблема (п. 19). На 29,78 Гц правило «интервал > 2 медиан» принимает дрожание интервалов за потерю. Около 85 % из 324 разрывов LT1 — не потери. Сейчас скан насчитывает 334 потерянных кадра, явных потерь около 10.

Предложение:

1. Колонка **Interval, ms** = 1000 / FPS: средний период, с которым работает конвейер. Подсказка: медиана сырых интервалов.
2. Потери по проверке окна: для каждого разрыва сумма 30 интервалов до и 30 после, делённая на период, минус число интервалов. Остаток ≥ 0,5 — потеряно round(остатка) кадров, время = кадры × период.
3. Что это даёт на LT1 (данные отчёта, `docs/data-flow/scripts/dfr_gapwindow.json`):
   - 29,78 Гц: потери у 49 из 324 разрывов, 65 кадров в 26 сессиях (сейчас скан пишет 334 кадра в 55 сессиях);
   - 19,76 Гц: 1 разрыв, 3 кадра (LT1_J03_2D);
   - точность: в контрольных окнах без разрыва остаток ≥ 0,5 у 3,4 %, то есть около 11 из этих 49 могут быть дрожанием;
   - бесспорные потери (интервал > 2,5 медианы): 4 разрыва, 10 кадров, 3 сессии.
   Поэтому Details делит потери на две строки: «certain» (интервал > 2,5 медианы или остаток ≥ 1,5) и «probable» (остаток 0,5–1,5).
4. `dropped_frames` ставится, только если найден хотя бы 1 потерянный кадр. Details: «3 frames lost (134 ms) at 12:03.4, certain». Одно дрожание — без аномалии, строка INFO «timing jitter» в Details.
5. Это меняет только аномалии. Они не входят в хэши этапов: после Rescan ничего не пересчитывается.
6. FPS пока не менять. FPS входит в хэш MC (п. 18). Новое правило FPS после Rescan пересчитало бы MC и всё дальше у 55 сессий LT1. Сначала убрать FPS из хэша MC так, чтобы готовые MC не устарели, потом менять правило FPS (FPS по длительности с учётом найденных потерь).
